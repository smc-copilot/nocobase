## Context

ADR-001 proposes the Hub as the only Person authority. This ADR fixes the identifiers and uniqueness rules P2 is allowed to implement. They are still Proposed. They are written so a later Broker choice can plug in without renaming people, and so an unproven vendor capability is not assumed.

The Casdoor plugin's uniqueness key is `providerIssuer` + `providerSubject` inside one app database. That fact supports "same email, different subject, do not merge" for a local user. It does not define a Hub Person. No live directory was queried in this pass.

## Decision

### personId

`personId` is a UUID generated by the Hub when the Person is created. It is immutable. It does not change when employee number, email, mobile, username, department, or status changes. It is not derived from those fields. ULID remains a PRD-permitted alternative and is not the proposed form, because current authentication and Casdoor provisioning already allocate ids with UUID.

A merged Person keeps the surviving `personId`. The retired id becomes an alias. Callers that still hold the retired id resolve it to the survivor. They do not receive a new random id.

### Person fields

Proposed Hub fields follow PRD 6.1.

| Field                    | Rule                                                                          |
| ------------------------ | ----------------------------------------------------------------------------- |
| `personId`               | UUID, primary identity, immutable.                                            |
| `employeeNo`             | Nullable. Uniqueness scope is below.                                          |
| `username`               | Nullable enterprise login name. Mutable. History kept on change.              |
| `displayName`            | Required display name.                                                        |
| `legalName`              | Nullable.                                                                     |
| `email`                  | Nullable, mutable, never the Person key.                                      |
| `mobile`                 | Nullable, mutable, never the Person key.                                      |
| `organizationId`         | Nullable primary organization.                                                |
| `departmentId`           | Nullable primary department.                                                  |
| `status`                 | `pending`, `active`, `disabled`, `archived`.                                  |
| `sourceAuthority`        | Attribute authority described below.                                          |
| `version`                | Monotonic integer, incremented on each change.                                |
| `createdAt`, `updatedAt` | Set by the Hub.                                                               |
| `disabledAt`             | Set when status becomes `disabled`. Cleared when the Person is enabled again. |

People are disabled or archived. Ordinary administration does not physically delete them.

### Identity uniqueness

A Person may have many identities. One active identity belongs to one Person.

The stored uniqueness key is (`providerId`, `identityKey`). `identityKey` is the canonical external key for that provider instance:

| Provider type                            | `identityKey`                                                                                                                                                 |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| OIDC, including a future Casdoor adapter | Normalized issuer plus the provider subject.                                                                                                                  |
| LDAP / Active Directory                  | The immutable external id (`objectGUID`, `entryUUID`, or the equivalent the adapter documents). A DN is a display attribute.                                  |
| OAuth2 UserInfo                          | The stable subject from UserInfo. A display name is not a subject.                                                                                            |
| Manual                                   | The Hub manual account id.                                                                                                                                    |
| OA LTPA                                  | Verified employee number, interpreted with the organization rule below. Meeting's existing LTPA path stays a separate mechanism until a later stage binds it. |

Issuer normalization, proposed for P2 tests: trim, drop one trailing slash, and compare scheme and host case-insensitively. The subject is stored exactly as the provider issued it and compared as an opaque string.

Uniqueness applies to identities in `active` or `pending`. An `unlinked` or `disabled` row stays in the table as history. A new active link for the same (`providerId`, `identityKey`) is allowed only when no active or pending row already holds that key, and the new row gets a new `identityId`. The physical index has to express that in a dialect-safe migration. This ADR does not choose a partial-index SQL dialect.

Resolution order after a successful upstream authentication, from PRD 8.1:

1. An existing (`providerId`, `identityKey`).
2. An existing immutable external id for that provider.
3. A verified employee number that is unique under the rule below, and only when that provider's policy allows employee-number match.
4. An approved manual link.
5. Otherwise a conflict or an approval queue. The login does not guess.

### Email and mobile

Email and mobile are attributes. They are not match keys. Two subjects that share an email stay two identities and, unless an administrator merges them under the merge rule, two Persons. The same rule applies to mobile and to display name.

Email may be shown as a hint on a link-preview screen. Verification of email or mobile records that the attribute was checked. Verification still does not auto-link. A mobile change is stored as unverified until a verification step confirms it. The verification channel itself is not built in P1.

An application database may still enforce its own unique email on the local `user` table. That constraint is an app projection problem (ADR-004). It must not reach back and merge Hub Persons.

### employeeNo uniqueness scope

`employeeNo` is unique per organization: at most one non-archived Person for a given (`organizationId`, `employeeNo`) when `employeeNo` is not null. Null employee numbers are allowed on many Persons. A Person with no organization is in a single unscoped bucket, so two unscoped Persons cannot share an employee number.

The enterprise has not confirmed a global employee-number namespace. If it does, the scope can tighten to a global unique employee number in a later ADR before any production migration relies on it. Until then, organization scope is the rule.

A second identity that presents an employee number already held by another Person in that scope does not auto-match. The Hub writes a conflict and waits for an administrator. Provider policy may still use a unique verified employee number as resolution step 3 when the number matches exactly one Person. A duplicate is a conflict, not a coin toss.

### Unlink and history

Unlink sets the identity to `unlinked`, records who did it and why, and emits an audited unlink. The row remains. Re-bind is a new audited action. One external identity is never actively linked to two Persons. Binding history is readable after unlink.

### Merge

Merge is a high-risk, approved operation. Unattended bulk merge is out of scope.

A merge requires a preview of both Persons' identities, memberships, Broker subjects, and known app bindings; a check that the same provider identity is not active on both; an authorized approver; one immutable audit event; an alias from the retired `personId` to the surviving `personId`; and a single transaction that moves links and memberships. Historical Person rows stay. Failure leaves both Persons as they were. App projections are repaired per app afterward, using the alias, and this ADR does not require every business database to update inside the Hub transaction.

### Attribute authority and locking

Each governed attribute records `sourceProviderId`, `sourceExternalId`, `sourceRevision`, `observedAt`, `isManuallyLocked`, and `lastChangedBy`. Directory sync skips a field whose `isManuallyLocked` is set. A Hub disable wins over a later directory update that still says the person is active, until an authorized enable.

Proposed default authorities, copied from PRD 8.5 as policy rather than as a measured directory:

| Attribute                    | Default authority                                  | Manual change                                                           |
| ---------------------------- | -------------------------------------------------- | ----------------------------------------------------------------------- |
| `employeeNo`                 | HR, LDAP, or an approved administrator             | High-privilege approval.                                                |
| `displayName`                | Enterprise directory, or an approved administrator | Overridable when configured.                                            |
| `email`                      | Enterprise directory                               | An administrator may override it, and the new value needs verification. |
| `department`, `organization` | Enterprise directory                               | Store the source version with the change.                               |
| `status`                     | Hub, or the designated authoritative directory     | Disable wins.                                                           |
| `mobile`                     | Directory or a verified manual edit                | A change needs verification.                                            |
| Avatar                       | The person or the directory                        | Ignored for matching.                                                   |

No HR feed was connected in this pass, so "HR is authoritative" is a default to encode, not an observed integration.

### Broker subject

The Broker must give every app a stable `sub` that does not carry email, employee number, or display name.

Preferred contract: OIDC `sub` is the Hub `personId`. The same person keeps that `sub` when they authenticate with a different upstream provider.

Fallback, only if the selected Broker cannot emit that `sub`: the Hub stores an immutable mapping (`brokerId`, `brokerSubject`, `personId`, `status`). One Broker subject maps to one Person. One Person has one active subject per Broker issuer. The mapping is created by the Hub from `personId`. It is never inferred from email or display name. The Broker's internal user id and the `personId` are both recoverable from audit.

The Broker product is undecided, so P2 may reserve the mapping as Hub data and must not call a Broker to fill it. ADR-004 tells the app which claim to read once a Broker exists.

## Consequences

P2 uniqueness tests have a clear expected result: the same (`providerId`, `identityKey`) cannot attach to two active Persons; the same email with two subjects does not merge; a repeated employee number in one organization becomes a conflict. Production data is not loaded to prove these rules.

## Open questions

Whether employee numbers are globally unique in the real enterprise. The exact dialect-safe shape of the active-identity unique index. Whether the eventual Broker can use `personId` as `sub`. Who is allowed to approve a merge, which is an authorization settings item in P2 and not a role name invented here.
